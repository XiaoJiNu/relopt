# ZC 自采数据 GT 与 Reloc3r 微调：讨论结论

- 日期：2026-10-22（Asia/Shanghai）
- 仓库：`git@github.com:XiaoJiNu/relopt.git`（本地：`/data/code/reLocation-all/relopt`）
- 相关文档：`docs/算法优化/ZC数据微调Reloc3r与XFeat并回测方案_Reloc3r优化方案_202610131710.md`
- 背景：梳理「当前自采 GT 能否满足 Reloc3r 微调与 cm 级验收」及后续正确采数/写 pose 方式

---

## 0. 总结论（先看这段）

| 用途 | 当前 `/map` → `.pose.txt` | 判定 |
| :--- | :--- | :--- |
| **训练 Reloc3r**（相对旋转 + 平移方向） | 同轨迹内相对可用；跨包有标签噪声但通常可训 | **基本满足** |
| **验收绝对重定位**（沿航向 &lt;10 cm / 跨航向 &lt;3 cm / 角 &lt;0.2°） | db 与 query 是两套独立 `/map`，互差约 7–12 cm / 0.1–1.3° | **不满足当尺子** |

一句话：

- **训练问的是**：两帧相对怎么转、往哪走 → 现有 `.pose.txt` **可以用**。
- **验收问的是**：query 在地图里绝对在哪、准到几厘米 → 必须把 db/query **写到同一 ENU**（RTK+杆臂等），不能继续拿「两次 `/map` 互掐」当厘米级尺子。

文档难懂，主要是因为把「训练标签够不够」和「评测尺子准不准」缠在一起了。

---

## 1. Reloc3r 到底要什么 GT

仓库侧（`ZcRelpose` + `loss.py`）约定：

- 每帧：去畸变图 + 内参 K + **`camera_pose` = 4×4 c2w（米制）**
- 训练对：`(db 图, query 图)`
- **相对位姿不单独存文件**，loss 里现场算：`gt = inv(pose_db) @ pose_query`
- 监督：旋转角误差 + **平移方向**角误差（平移会单位化），**不强迫学米制尺度**

因此微调需要的不是「绝对厘米级 RTK 真值」本身，而是：**两帧在同一坐标系下的相对朝向 + 相对位移方向大致正确**。

## 2. 当前 ZC 数据处理在做什么（有没有硬伤）

### 2.1 流水线（`eval_zc.py extract`，已定稿）

1. mcap 读图像 + `/map`（车端定位融合位姿）
2. 图像去畸变，按时间最近邻对齐 `/map`（&gt;100 ms 丢帧）
3. 外参链：`T_map_cam = T_map_lidar @ R_BL @ T_cam_lidar`（必须含 `R_BL`；旧链已废弃）
4. 写出 `frame-XXXXXX.color.png` + `.pose.txt`
5. MegaLoc 生成 db–query 对；过滤基线 &lt;0.15 m 或 &gt;10 m

### 2.2 格式侧

抽样 `zc_fix` 的 pose：旋转行列式≈1，相机朝下合理，外参守卫会拦错链 → **格式没有硬伤**。

### 2.3 训练侧软约束

1. **外参链**：含 `R_BL` 的可用；旧 glm 链数据须重 extract（否则约 2 m 级姿态错）。
2. **跨包相对标签**：跨包 `/map` 朝向/位置基准差会进相对 GT（尤其跨天 yaw 可到约 1°）→ **能训，但角度上限被污染**。
3. **配对基线**：&lt;0.15 m 接近 `/map` 噪声病态；&gt;10 m 共视弱 → 现过滤合理。
4. **检索分布**：训/测候选应同源（勿 NetVLAD 训、MegaLoc 测）。

### 2.4 评测侧

跨包 `/map` 互差（约位置 p50 **7.5–11.5 cm**、朝向 **0.08°（同天）～1.3°（跨天）**）已经大于 cross&lt;3 cm、角&lt;0.2° → **无法诚实验收量产指标**。这是尺子问题，不是「标签文件格式写错」。

---

## 3. 问题定义：为什么 db 和 query 不是同一个包

这是**重定位问题定义**，不是数据处理写错：

| 角色 | 含义 |
| :--- | :--- |
| **db 包** | 事先建好的地图轨迹 |
| **query 包** | 另一次行驶、要定位的轨迹（可同天/跨天） |
| **奇偶切分** | 只切 **query 包内部帧**（防泄漏）；**db 不切**（部署时地图本就是固定另一条录包） |

训练/评测相对与绝对，都建立在「query 锚到 db 坐标系」上。A、B 若各用各的 `/map`，同一物理点坐标本就不完全一样 → 这部分误差进数字，**改网络消不掉**。

- **同包内**两帧做差：慢漂移多抵消 → 相对标签对训练仍可用。
- **跨包**当评测尺子：尺子比 3 cm / 0.2° 目标还粗 → 测不出达标。

## 4. 讨论中澄清过的几个易混点

### 4.1 「跨包 map 误差 &gt; 指标 → 训不出达标」对不对？

| 说法 | 判定 |
| :--- | :--- |
| 跨包 `/map` 互差已经大于 cross&lt;3 cm、角&lt;0.2° | **对** |
| 用现在这套 GT **验收**，数字上永远测不出达标 | **对** |
| Reloc3r **完全训不出有用的相对位姿** | **不对**（相对监督仍可学） |
| 因此物理上绝对不可能到 cm | **说太死**；主因是尺子/绝对标签不一致，换统一真值后才能量模型好不好 |

更准确：**现在卡的是「量不准 + 跨包绝对标签不一致」**，不是「相对网络完全没法训」。

### 4.2 「一个 query 只对应一个 db → 相对位姿就会很小」？

**不对。** 相对位姿大小只取决于**这一对匹配图**的空间/朝向差，与「几个包」无关。基线过滤管的是匹配对距离，不是包数量。

### 4.3 「多 db 各用各的 `/map` 会伤学习；单 db↔单 query 影响就不大」？

**大体对，但不是零影响。**

| 设定 | 对 Reloc3r **相对**学习 |
| :--- | :--- |
| 多 db、各用各的 `/map`、不统一 | 影响大，标签易自相矛盾 |
| 单 db ↔ 单/多 query（仍各用 `/map`） | **影响小很多，通常可训**，仍有跨会话偏差噪声 |
| 单 db，但要报 cm/0.2° **绝对**验收 | 仍不够，必须统一坐标真值 |

### 4.4 推荐数据组织（已确认）

> 一个场景最好 **一个 db**；query 可跨天多录；**所有包相机 pose 写到同一 ENU** → 相对 GT 误差会小很多、也一致很多。

补充：不是数学上的零，还剩 RTK 噪声、杆臂/外参、时间对齐等（通常厘米～分米，取决于 RTK 质量）。

---

## 5. 「所有包写到同一 ENU」是什么意思、为什么要做

### 5.1 含义

每个 mcap 的 `/map` 往往是**那一次开机自己的地图系**（db 原点 ≠ query 原点）。

- **RTK**：天线在固定坐标系（常用 ENU：东-北-天）中的位姿，跨包可共用。
- **杆臂**：天线 ≠ 相机光心，需刚性外参（天线→车体/雷达→相机）。
- **重写**：每帧 `T_ENU_cam = T_ENU_antenna @ 杆臂/外参链`，覆盖或旁路原来的 `.pose.txt`。

做完后 db、query 都在同一 ENU → 相对 GT 与绝对评测共用一套真值。

### 5.2 为什么必须做

相对 GT 与绝对误差都靠两帧 pose 运算：

```text
T_rel = inv(pose_db) @ pose_query
```

若 `pose_db`、`pose_query` 各用各的 `/map`：

- `T_rel` 混进「A 地图相对 B 地图歪了多少」→ 不是纯相机相对运动；
- 网络吃带毒相对标签；
- 验收用两套坐标互掐 → 误差地板≈跨包 `/map` 差，和模型缠在一起。

统一 ENU 后：训练标签和验收尺子说的是**同一套几何**。这不是为了好看，是为了减法本身正确。

## 6. 要满足要求应该怎么做

### 6.1 目标 A：把 Reloc3r 在 ZC 域微调好（相对更准）

1. 继续：`extract`（定稿外参链）→ MegaLoc 制对 → 基线过滤 → `ZcRelpose` 微调。
2. 可选加强：RTK+杆臂重写各包 pose 后再算相对 GT；或混一部分同包内、基线 0.5–5 m 的对。
3. 可混一点公开域防遗忘；编码器小学习率或冻结。

### 6.2 目标 B：验收沿航向 &lt;10 cm / 跨航向 &lt;3 cm / 角 &lt;0.2°

1. **先换尺子（M2）**：逐包 RTK+杆臂，重写/旁路 `.pose.txt`；校正跨包朝向基准；用新真值重算误差。
2. **再改聚合（M1）**：灾难帧多为选择/投票问题，不只是回归网络精度。
3. cross&lt;3 cm：RTK 自身也可能有 ~5–7 cm 底 → 可能需放宽口径或更高精度真值（产品决策）。

### 6.3 目标 C：重新录包生成训/验（可执行简流程）

**A. 录包（最少 2 次，同一场地）**

1. **db**：跑覆盖工作区；开图像 + `/map` + **RTK** + TF/外参相关。
2. **query**：另一次（同天或跨天）再跑，路径覆盖同一区域。
3. RTK 尽量 **fix**；天线与标定杆臂一致。
4. 图像约 2 Hz 即可训 Reloc3r。

**B. 抽帧写 pose（每包各做）**

1. 去畸变 + 时间对齐（可沿用现 `extract`）。
2. **优先 RTK+杆臂写 `T_ENU_cam` → `.pose.txt`**；`/map` 仅备份。
3. 无 fix 帧丢掉或单独标记，不进训/验。

**C. 组训练对 / 验证对**

1. db 全量进检索库；query 奇偶（或按时段）切：偶训奇验。
2. MegaLoc 为每个 query 找相似 db → pair npy。
3. 过滤基线 &lt;0.15 m 与 &gt;10 m。
4. 相对 GT 仍：`inv(pose_db)@pose_q`（此时已在同一 ENU）。

**D. 使用**

- 训练：相对 R + t 方向微调 Reloc3r。
- 验收：预测锚在 **db 的 ENU pose**，与 **query 的 ENU pose** 比沿/跨航向与角度——**不再**与另一次 `/map` 比。

**E. 暂时做不到 RTK 重写时**

- 仍可按现流水线训相对模型。
- **不要**用跨包 `/map` 宣称 cm/0.2° 达标；验收等统一真值，或先只报相对/粗粒度指标。

---

## 7. 可记口诀

1. **一场景一 db**；query 可跨天；配对用检索，不是「一个包奇偶切分就等于重定位」。
2. **相对大小 ≠ 几个包**；= 匹配两帧空间差。
3. **多套未对齐 `/map` 拼进同一训练集** → 相对标签易打架，应避免。
4. **统一 ENU（RTK+杆臂）** → 相对监督干净 + 绝对验收才诚实。
5. Reloc3r **不需要**深度图当相对位姿标签；深度是 XFeat 等几何对应另一条线的事。
