**术语速查**（本文反复出现的几个词）：
- **db 帧 / query 帧**：db = 地图包里预先建好的帧（部署时的"地图"）；query = 待定位的当前帧。二者来自**两个不同的录包**。
- **/map**：车端定位算法（轮速/IMU/RTK 融合）实时输出的位姿话题，被当评测真值用，但它不是绝对真值。
- **真值误差 / GT 底**：/map 自己相对独立基准（RTK）的偏差。评测数字里混着这部分，与模型无关。
- **沿轨 / 跨轨（along / cross）**：把定位误差向量投影到"车行进方向"和"垂直行进方向"两个分量。
- **灾难帧 / 尾部**：极少数误差爆掉（>0.5 m，最差 30 m）的帧；它们主导 mean，是模型侧最大的可改空间。
- **bm3 / 聚合**：把 query 对多个 db 候选各自的相对位姿"投票平均"成一个最终位姿的规则（bm3 = 以候选位置中位数为锚、保留 3 m 内候选）。
- **oracle**：用 GT 作弊选最优候选，只作精度上界参考，不可部署。
- **headroom**：还有多少可提升空间。

## 0. 结论先行

**一句话：三个目标里，沿航向 <10 cm 靠杀灾难帧就能达到；跨航向 <3 cm 和角度 <0.2° 目前"测不出来"——不是模型不够准，而是评测用的真值（/map）本身在 cm 级和 0.1° 级上不准，尺子刻度比目标还粗。**

| ---------- | ----------- | ---------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------------------------------------ |

| 角度       | mean <0.2° | 0.42 / 0.47 / 0.31°         | 两包朝向基准差 0.08°（同天）/ **1.31°**（跨天）/ 0.55°（0923） | **当前测不出**：跨天两包朝向基准差 1.3°，是目标 0.2° 的 6 倍——这个差会 1:1 进到测出的角度误差里 |

**两条行动线，顺序不能反：**

1. **先修尺子（M2：GT 升级）**——把真值从"两包各自的 /map"换成"RTK 锚定+杆臂建模后的轨迹"（本会话已实测跑通：/map 对 RTK 的绝对偏差从表面上的 0.39 m 降到 5–7 cm，其中 0.34 m 是 RTK 天线杆臂没有建模造成的假误差）。不修尺子，cross/angle 两个目标的任何"优化"都是在噪声里挑数字。
2. **再修模型（M1：杀灾难尾部）**——这是模型侧唯一有大空间的杠杆：跨天 ep_mean 0.24 m 里 **69% 来自 9 个 >0.5 m 的灾难帧**（最差两帧 30.4 / 25.9 m），剔掉后沿轨 mean 从 0.150 m 降到 **0.043 m**。问题出在候选投票聚合（bm3）被 look-alike 错误簇骗过，不是回归网络不准（§2.1 有逐帧取证）。

其余（M3 检索统一——数据已备好、M4 遗忘、M5 角度专项、M6 尺度）为二线，见 §4。

**可执行性 / 有效性 / 量产就绪 三分：**

## 1. GT 可行性分析（目标 1：这些精度能不能达到）

### 1.1 评测到底在跟什么比（先搞清楚数据从哪来）

**一个"场景"= 两个不同的录包**（不是同一个包切两半）：

| 场景 | db 包（建地图那次录制） | query 包（考重定位那次录制） | 两包关系 |
| ---- | ---------------------- | --------------------------- | -------- |
| 草坪同天 | 20260921_**064638** | 20260921_**062224** | 同一天，相隔 24 分钟，同一条环线 |
| 草坪跨天 | 20260921_**064638** | 20260920_**081533** | 隔一天，同一条环线 |
| 大楼 0923 | 20260923_**055425** | 20260923_**060415** | 相隔 10 分钟，同一区域 |

奇偶切分切的是 **query 包内部的帧**（偶数帧训练、奇数帧评测）——它解决的是"训练/测试帧不重叠"的防泄漏问题，**和 db 帧没有关系**。db 帧永远来自另一个包（db 包 = 部署时预先建好的地图，这是重定位问题的定义：在地图包里检索、给 query 帧定位）。

**评测每一帧的算分过程**（以跨天为例）：

```
模型预测的 query 位姿 = db 包里某帧的位姿(来自 064638 包的 /map)  ∘  模型算出的相对位姿
评测用的 query 真值   = query 帧的位姿(来自 081533 包自己的 /map)
误差 ep = 两者的位置差；eθ = 两者的朝向差
```

关键：**预测和真值各自吃了不同包的 /map**。064638 包的 /map 是那次开机时车端定位算法跑出来的一条轨迹；081533 包的 /map 是第二天另一次开机跑出来的另一条轨迹。两次独立运行各有各的漂移和基准偏差——同一个物理位置，两条轨迹报出来的坐标不完全一样。

疑问：db帧和query帧不是同一个录包里面出来的吗，怎么两个成了两个包？我理解是实际录的包，分奇偶来作为训练测试集，那测试集中每个qurey对应的关键帧应该也是同一个包才对，如果是同一个包，应该是1次定位跑出来的才对，然后，这些误差到底来自哪里？

> **答**：不是同一个包，上表已列——每个场景 db 帧来自 db 包（地图包），query 帧来自 query 包，奇偶切分只切 query 包内部的帧，db 包不切（见上游方案 §3.1"db 帧不切分"）。所以评测真值和预测锚点确实来自**两次独立的定位运行**。
>
> **这些误差到底从哪来**——三步说清：
>
> 1. **每个包的 /map 本身不是绝对真值**。/map 是车端定位算法（轮速/IMU/RTK 融合）的输出，对独立基准（RTK 原始定位）有 **5–7 cm 的位置偏差和 0.1°级的朝向偏差**（§1.2 表：用杆臂建模后实测）。同一个包内部，这个偏差随时间慢变、高度相关，所以**同包内两帧做差**时大部分抵消（这就是为什么单包评测看起来精度很高）。
> 2. **但评测做的是跨包做差**：db 帧位姿（A 次运行的 /map）∘ 相对位姿，对比 query 帧位姿（B 次运行的 /map）。A、B 两次运行各自漂了不同的量、朝向基准也各自偏了不同的角——**做差时不抵消，剩下的分歧直接进误差指标**。实测这个分歧：位置 7.5–11.5 cm p50（两包各 5–7 cm 的偏差相减，量级正对上），朝向差 0.08°（同天）～1.31°（跨天，用双天线航向独立测出）。
> 3. **为什么跨天最大（1.31°）**：实测事实是各包的 /map 朝向对双天线航向的固定 offset 不同（db_064638 93.31° / q_062224 93.23° / q_081533 92.00° / 0923 两包 91.42°/90.87°）——即**每次运行 /map 的朝向基准各自偏了 ~1° 量级，且互不相同**；同天两包 offset 几乎一样（差 0.08°），跨天差 1.31°。偏置的物理来源（初始化时的航向对准状态 / 融合器零偏估计 / 天线安装角当次标定）**未直接验证**，属推测项——但"偏置存在且跨包不同"是双天线独立实测，不依赖推测。
>
> 所以"误差从哪里来"的答案是：**测出的 ep/eθ = 模型真实误差 + 两包 /map 的分歧（7.5–11.5 cm / 0.1–1.3°）**。第二项与模型无关、无法靠改模型消除，只能靠换真值基准（M2：用 RTK+杆臂建模重构真值，或校正两包朝向基准差）去掉。当目标（3 cm / 0.2°）小于第二项时，指标就无法反映模型好坏——这就是"尺子刻度比目标粗"的含义。

### 1.2 实测：/map 真值到底多准（本会话直读 4 个 mcap 包，探针已存 `relopt/scripts/gt_probes/`）

按"从粗到细"四层测。前三层说明 /map 单包内部很好，第四、五层说明**跨包之间不一致**——评测吃的正是跨包这一层。

| # | 测什么 | 怎么测 | 结果 | 说明 |
| - | ------ | ------ | ---- | ---- |
| 1 | /map 自己声称的精度 | 读消息里的 covariance 字段 | 位置 σ 恒等于 0.1 m、旋转 σ 恒等于 2.86°，所有包所有时刻一个数 | 是写死的占位值，**不能当精度依据** |
| 2 | /map 逐帧平滑度 | 每帧位置 vs 前后 1 s 窗口的二次拟合 | 偏差 p50 仅 0.09–0.13 cm | 轨迹非常平滑，**没有高频抖动**——误差不来自逐帧噪声 |
| 3 | /map 朝向局部准不准 | /map 转过的角度 vs 陀螺仪积分的角度（1 s / 3 s 间隔） | 差 0.09–0.12°（1 s）、0.27–0.35°（3 s） | 单包内 /map 的**相对朝向精度 ~0.1°**，够用 |
| 4 | /map 绝对位置准不准 | 把整条 /map 轨迹和 RTK（独立真值）对齐比 | 旧口径（直接对齐）p50 **0.38–0.43 m** → 这就是旧文档"0.39 m GT 底"的出处；本次加入 **RTK 天线杆臂建模**（天线不在车体原点，偏 ~0.4 m，随车头朝向转）后降到 p50 **4.9–7.1 cm** | **"0.39 m"里 ~0.34 m 是没建模天线杆臂造成的假误差**；/map 的真实绝对精度是 5–7 cm |
| 5 | **两个包的 /map 互相一致吗**（评测真正消费的） | db 包和 query 包各自用第 4 层方法锚到 RTK 后，比较同一物理位置处两包的相对位移/相对朝向 | 位置分歧 p50 **7.5–11.5 cm**（沿轨 4–7、跨轨 3–7），与两帧距离无关（0.3 m 到 60 m 都一样）；朝向分歧：双天线独立测得两包基准差 **0.08°（同天）/ 1.31°（跨天）/ 0.55°（0923）** | **这就是评测数字里混入的真值误差**：两包各 5–7 cm 的绝对偏差不同向，相减后剩 7.5–11.5 cm；朝向同理剩 0.1–1.3° |

第 5 层的读法：评测公式里，预测锚在 db 包的 /map 上、真值取自 query 包的 /map——两条轨迹在同一地点本来就差 7.5–11.5 cm / 0.1–1.3°，**这部分无论模型多准都会出现在 ep/eθ 里**。

### 1.3 逐目标判定（把 §1.2 的数字对到三个目标上）

**沿航向 <10 cm —— 能达到，但这是"杀尾部"问题，不是"提精度"问题。**
真值自身误差沿轨 4–7 cm；模型当前（剔掉灾难帧后）沿轨 mean 3.9/4.3/7.5 cm——已经贴着真值误差的水平。
含灾难帧的沿轨 mean 是多少？跨天 0.150 m（报告 §5），剔掉 >0.5 m 的帧后掉到 **0.043 m**——那 0.15 m 几乎全是 2–3 个灾难帧贡献的，不是普遍精度差。
→ M1 压掉灾难帧即可达标；但想再往下（比如 <5 cm）就进入真值误差区间，测不出来了，需要 M2。

**跨航向 <3 cm —— 现在的真值测不出这个精度。**
真值自身误差跨轨：大楼 3–4 cm、草坪 5–7 cm。**目标 3 cm 小于等于真值误差**。模型实测 cross mean 4.1–4.3 cm，其中大部分是真值误差而非模型误差——这种情况下把数字"优化"到 3 cm 以下没有意义（真值本身就在 3–7 cm 抖，你怎么知道测出的 2.9 cm 是模型变好了还是真值那帧恰好偏了？）。
→ 必须先做 M2 把真值误差降到 3 cm 以下才有判定条件。而且注意：RTK 自己也有 5–7 cm 误差，M2 做完跨包相对误差能到多少是未知数——cross<3 cm 可能最终需要更高精度的真值（全站仪标定点 / 多包联合平差）才能验证，这是决策点 D2。

**角度 <0.2° —— 现在的真值测不出，跨天差得最远。**
单包内 /map 朝向精度 ~0.1°（§1.2 第 3 层），本身够。问题在跨包：db 包和 query 包的 /map 朝向基准互差 0.08°（同天）/ **1.31°**（跨天）/ 0.55°（0923）。评测算 eθ 时这个基准差**原封不动进指标**——跨天场景就算模型角度误差为 0，测出来也是 ~1.3°，是目标 0.2° 的 6 倍。
→ 在换真值之前，angle<0.2° 无法验证。M2 校正两包朝向基准差之后：同天（基准差仅 0.08°）和 0923（0.55°）场景的模型真实角度误差（当前 med 0.34°/0.26°）才有机会逼近 0.2°；跨天必须先去偏置。

### 1.4 一句话回答目标 1

> 沿航向 <10 cm：**能达到**，靠 M1 杀灾难帧（中位数早就达标了）。
> 跨航向 <3 cm、角度 <0.2°：**不是模型不行，是尺子不行**——目标比真值自身的误差（跨轨 3–7 cm、跨包朝向 0.1–1.3°）还小，当前口径下既不能证明达标也不能证明不达标。先做 M2 换真值（RTK 锚定 + 杆臂建模 + 跨包朝向基准校正），再谈这两个目标。

## 2. 当前算法问题诊断（结合两份报告）

### 2.1 灾难尾部 = 模型侧唯一有大空间的问题

**现象**：每个场景都有极少数帧误差爆掉，它们主导了 mean。逐帧取证（微调权重、奇数评测帧、每帧 10 个候选全部 dump，`reloc3r/data/zc_sim3/cands_*_K10_ft_odd.npz`）：

| 场景        | ep_mean（含灾难帧）   | >0.5 m 的灾难帧数 | 灾难帧占总误差和的比例 | 最差 3 帧误差                  |
| ----------- | ----------------- | ----------- | ----------------- | ----------------------------- |
| 062224 同天 | 0.075 m           | 3 / 338     | 18%               | 1.54 / 1.36 / 0.94 m          |
| 081533 跨天 | **0.240 m** | 9 / 411     | **69%**     | **30.4 / 25.9 / 8.1 m** |
| 0923 大楼   | 0.105 m           | 7 / 407     | 9%                | 1.12 / 0.84 / 0.77 m          |

**灾难帧是怎么产生的**（以跨天两个 ~30 m 帧为例，逐帧查过）：

1. 草坪纹理重复 + 环线多次经过同一带，MegaLoc 检索的 top-5 候选里混进了**外观相似但位置差 ~28 m 的错误帧群**（错误帧彼此挨着，构成一个"错误簇"）。
2. 检索侧完全无法预警：这些帧的相似度 0.057–0.196，和好帧同分布；拿相似度/相似度差各种阈值扫，**一个灾难帧都抓不到**（bad_caught=0）。
3. 聚合侧被骗：bm3 的做法是"取 5 个候选推算位置的**中位数**当锚点，保留锚点 3 m 内的候选再平均"。中位数不看检索排名——5 个里 3 个是同一错误簇时，中位数落到错误簇上，3 m 半径反而把**正确的 2 个候选筛掉**，最后 3 个错误候选"一致投票"出 30 m 的结果。

**定性证据：是选择问题，不是回归问题。** 拿 GT 作弊选"top-5 里最好的 3 个"（oracle，只做上界参考），ep med = 0.030 / 0.036 / 0.044 m——候选池里**本来就存在**误差 <5 cm 的组合，现行聚合没选中它。网络回归得够准，错在投票规则。

### 2.2 聚合初测：把"中位数锚"换成"检索 top-1 锚"，跨天 mean −34%

思路：中位数 rank-blind（不看谁更像），而 MegaLoc 排第 1 的候选是外观上最可信的——用它的位置当锚。离线扫（零 GPU，`scripts/gt_probes/anchor_sweep.py`）：

| 场景   | K5_bm3（现行，中位数锚）ep_mean | K5_anchor1_r3（top-1 锚，3 m）ep_mean | K10_anchor1_r1.5（top-1 锚，1.5 m，池扩到 10）ep_mean |
| ------ | --------------------- | --------------------- | --------------------- |
| 062224 | 0.078                 | **0.067**       | 0.078 |
| 081533 | 0.247                 | 0.172                 | **0.164**          |
| 0923   | 0.104                 | 0.104                 | 0.107                 |

跨天 0.247→0.164（−34%），30.4 m 那帧被压掉（最差剩 25.9 m）。
**已知缺陷**：top-1 自己错时锚就错了（062224 有一帧从 2.4 m 恶化到 16.4 m）——所以方案是 **top-1 锚 + 中位数锚双判据**（两锚一致才用，不一致降权/回退），或交给时序 EKF 兜底（§4 M1）。

### 2.3 遗忘仍未过线（报告 §3 ❌）

mix50 补救后 MegaDepth terr med 1.976° vs 官方 1.561°（门槛 1.72°），仍 ❌。
混公开数据的比例这条路已经走到头（25%→50% 只把 2.05°→1.98°，几乎没动）。这是**机制问题**：lr 1e-5 + freeze_encoder 下，
relpose head 全参微调必然漂移公开域。需 LoRA/adapter 或降 lr（§4 M4）。

### 2.4 跨天场景整体看起来最差，其实只是尾部最差

跨天 ep_mean（含灾难帧）0.240 vs 同天 0.075、大楼 0.105——看着差 2–3 倍。但剔掉灾难帧后：ep_mean = 0.064 / 0.068 / 0.094 m，沿轨 mean = 0.039 / 0.043 / 0.075 m（顺序：同天/跨天/大楼，实测 `cands_*_K10_ft_odd.npz`）——跨天反而比大楼好。
→ **跨天的"差"全在尾部**，普遍精度三场景一致。所以跨天不需要单独的域适配，需要的是 M1（尾部抑制）+ M2（跨天朝向基准差 1.31°，§1.3）校正。

## 4. 优化方法（按可提升空间从大到小排序）

### M1 — 灾难尾部抑制（模型侧最大空间，跨天 ep_mean −34% 已初测）

- **现状**：跨天 9 帧 >0.5 m 占误差和 69%，最差 2 帧 ~30 m；检索侧无法预警（§2.1）。
- **机制**：bm3 用"候选位置中位数"当锚，不看检索排名；look-alike 错误簇占多数时中位数落到错误簇上，正确候选反被 3 m 半径筛掉（§2.1）。
- **方法（三选，可叠加）**：
  1. **聚合改锚定**（零 GPU，已初测）：锚从"候选位置中位数"换成"检索 top-1 候选位置"，或 top-1+中位数双锚（两锚一致才信，不一致降权/回退）。实测跨天 ep_mean 0.247→0.164。
  2. **时序 EKF gate3**（已实现，`relopt/scripts/ekf_fuse.py`）：优化实施记录 §1 已证 EKF 融合登顶综合分 0.819，靠的就是用时序连续性吸收 look-alike 翻转。把 Reloc3r 观测换成微调权重 + MegaLoc 候选，重跑 EKF。
  3. **候选池扩到 K=10 + 更紧一致性半径**：oracle best-3-of-5 = 0.03 m 说明池里有好候选，扩大池 + 一致性筛（两两一致 RANSAC）提高选中好子集概率。
- **预期**：跨天 ep_mean 0.24→0.07（剔尾水平）、ep_p90 0.15→0.11；沿轨 mean 全场景 <8 cm。
- **成本**：方法 1/3 零 GPU 离线可扫（候选已 dump）；方法 2 已有代码。
- **风险**：top-1 锚在 top-1 本身错时失效（062224 现一个 16.4 m）→ 必须 top-1+中位数双锚或 EKF 兜底，不能单用 top-1。
- **ponytail**：先上方法 1（改 ~10 行聚合，离线扫验证），EKF 已有不重写；方法 3 仅在 1+2 仍留 >5 m 残帧时加。

### M2 — GT 升级（验证 cross<3 cm / angle<0.2° 的前置，非模型改动）

- **现状**：评测真值 = 两包各自的 /map 跨包做差，真值自身误差 7.5–11.5 cm 平移 / 0.1–1.3° 朝向（§1.2）；旧文档"0.39 m"是绝对口径且含天线杆臂，**误导**（跨包相对做差时杆臂大部分抵消——注意：杆臂对绝对残差是主项，对跨包相对是次要项，两个口径别混）。
- **方法**：
  1. **RTK 锚定 + 逐包杆臂建模**（本会话已跑通拟合，`scripts/gt_probes/gt_analysis5.py`）：拟合 `enu = w·(p_map + R_yaw·v) + o`（v=天线杆臂、w=地图→ENU 旋转、o=平移），把 /map-vs-RTK 残差从 0.39 m 降到 **5–7 cm p50**。用此重构每包的车体真值 → 跨包相对真值误差从 7.5–11.5 cm 降到"两包杆臂/漂移一致的那部分"。
  2. **跨包朝向偏置校正**：双天线实测的两包 offset 差（0.08/1.31/0.55°）作为 db↔query 的朝向基准差，从 eθ 里扣除——这是 angle<0.2° 能否验证的关键。
  3. **（可选，更彻底）db+query 两包联合 BA / 闭合差平差**：把跨包相对基准统一到 RTK 闭环，消除两次定位跑各自的漂移。
- **预期**：可测量下限从"跨包 /map 7.5–11.5 cm / 0.1–1.3°"降到"RTK 锚定 5–7 cm / 去偏置后朝向"。届时 cross 与 angle 两个目标才可判定。
- **成本**：中（重算 pose.txt 或 eval 侧换真值源）；零训练。杆臂拟合脚本本会话已验证。
- **风险**：RTK 自身 5–7 cm 仍是硬底——**cross<3 cm 即便 RTK 锚定也可能测不到**，需更高精度真值（全站仪 / SLAM 闭合）才能验证 3 cm 级。角度去偏置后 SE 仍 0.29–0.43°（双天线噪声），0.2° 级验证需更多样本平均。
- **决策点 D2**：cross<3 cm 是否值得为它上全站仪级真值？还是把目标放宽到"RTK 可测的 5 cm 级"？这是产品口径决策，不是算法决策。

### M3 — 检索-回归统一重训（数据已备，§3）

- **现状**：MegaLoc 制对 npy 已生成（§3.1），训练/评测候选分布已统一，但未重训。
- **方法（未来命令，未执行）**：用 `zcM_*/zc9M_*` 对重跑 `finetune_zc.sh`（改 `pairs_info_file_mask` 指向 zcM），30 epoch 混训。
- **预期**：域适配一致性↑，减少 train/eval 错配；幅度待测（标签同源，主要影响候选覆盖）。
- **成本**：重训 6–8 h GPU；全部微调基线作废重跑。
- **风险**：收益可能有限（标签不变）；建议在 M1+M2 之后做，一次重训吃全部改进（D1）。

### M4 — 遗忘补救机制升级（报告 §3 ❌ 未过线）

- **现状**：mix50 仍 terr med 1.98° vs gate 1.72°；调混比这条路已走到头（25→50% 只动 2.05→1.98）。
- **方法**：
  1. **LoRA / adapter**（推荐）：relpose head 插低秩增量，冻主干 → 公开域漂移被结构限制。需改 `train.py`（中等）。
  2. **降 lr 到 5e-6**（零改）：域适配够、漂移小。
  3. **更大公开锚**：MegaDepth 全 1500 对（现只用前 750）+ 换遗忘 eval 子集。
- **预期**：terr med 压回 <1.72°（门槛），同时保域适配增益。
- **成本**：方法 2/3 零改即可试；方法 1 需改训练代码。
- **风险**：LoRA 可能限制域适配上限（增量秩太低学不动 ZC）；需扫秩。

### M5 — 角度精度专项（依赖 M2）

- **现状**：eθ mean 0.31–0.48°、med 0.25–0.42°；目标 mean<0.2°。
- **机制**：测出的 eθ = 跨包朝向基准差（0.1–1.3°，真值误差）+ relpose 网络自身的旋转误差。单包内 /map 朝向已 0.1° 级（够），瓶颈是**跨包基准差**（M2 才能扣掉）+ 网络旋转本身。
- **方法**：
  1. **先 M2 扣掉跨包朝向基准差**，再看模型真实角度误差——扣除后 0923（med 0.257°）和同天（0.344°）可能已接近 0.2°。
  2. **recoverPose 几何解 vs 回归解融合**（优化实施记录 P0-1）：0923 大交会角场景用几何解真增益（med −41%），草坪小基线场景几何解纯损害 → **必须按交会角门控**（db 候选间距 <1 m 时回退用 db 帧朝向）。
  3. 候选旋转已用四元数中位数（对离群稳健），无需改。
- **预期**：扣基准差 + rc 门控后，0923/同天 eθ mean 有望 <0.2°；跨天需先扣 1.3° 基准差。
- **成本**：方法 1 = M2；方法 2 已有 `eval_zc_xfeat_rc.py` 的 rc 实现可移植。
- **风险**：草坪小基线用几何解有害，门控判据（交会角/候选间距）必须严格，否则负增益。

### M6 — 沿航向尺度约束（架构性，优先级低）

- **现状**：沿轨是单目相对位姿回归的固有弱项（无绝对尺度）；但微调后沿轨 med 已 2.3–5.2 cm（很好），mean 受灾难帧拖累（M1 解决）。
- **机制**：单目 relpose 无绝对尺度，ZC 慢速小基线沿轨方向不可观（`references/retrieval-pair-protocol.md`）。
- **方法**：时序/odom 给尺度（EKF 已兜底）；或训练加 depth 监督（LiDAR 投影，`AirSLAM/rosless/extract_zc.py` 有现成投影器）给沿轨尺度。
- **预期**：沿轨尾部收窄。
- **成本**：depth 监督需 LiDAR 投影 + 改 loss。
- **风险**：当前沿轨已达标，**优先级最低**，仅在 M1 后沿轨尾部仍 >10 cm 才做。

## 6. 执行顺序（评审通过后）

```
第 0 步（已完成，本会话）：MegaLoc 制对 npy 生成 + GT 五层精度实测 + 候选 dump + 聚合离线扫
        ↓
第 1 步 M2（GT 升级，零训练，前置）：
   - 逐包杆臂+旋转拟合，重构 RTK 锚定的车体真值（gt_analysis5.py 已跑通，需落成 eval 真值源）
   - 双天线跨包朝向偏置校正表
   - 用新真值重算当前微调权重的 ep/eθ → 得到"去掉真值误差后"的真实模型精度基线
        ↓
第 2 步 M1（尾部抑制，零 GPU 离线扫 → 落 eval）：
   - 聚合锚定改 top-1 / top-1+中位数双锚（离线扫已 dump 候选，秒级验证）
   - 选定后改 eval_zc_sim3.py 聚合段，三场景复测
   - 若仍留 >5 m 残帧 → 接 EKF gate3（已有代码）
        ↓
第 3 步 判定 cross<3cm / angle<0.2°（在 M2 的新真值下）：
   - 达 → 收工
   - 未达且真值误差已 <目标 → 归因模型，进 M5（角度）/ M6（尺度）
   - 未达但真值误差仍 ≥目标 → 目标不可验证，回 D2 决策（放宽目标 or 上更高精度真值）
        ↓
第 4 步 M3（检索统一重训）+ M4（遗忘机制）：
   - 用 zcM 对 + LoRA/降 lr 重训一次，同时吃 M1 聚合改进
   - 遗忘检查过线 → 出最终报告
```

**为什么这个顺序**：M2 不做，后面所有 cross/angle 数字都混着真值误差，无法判断 M1/M3/M5 是否真有效；
M1 零 GPU 且可提升空间最大，紧跟 M2；M3 重训放最后，一次吃到 M1 聚合 + M2 真值 + M4 机制，避免基线反复作废。
